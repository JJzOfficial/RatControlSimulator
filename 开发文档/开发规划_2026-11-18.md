本文是规划与建议，不修改已有规格。第 5 节列出的建议需要你确认后才进入实施；第 1 节是你已经给出的决定，直接执行。AGENTS.md 的基线沿用规则继续有效，本文任何条目都不授权重写已验收的 P0 / RiverbendDemoV4。

## 2. 现状判断

工程 `G:/MyGame/RatControlSimulator` 已在原 P0 入口上接入六图、18 单、45 种生物、全部装备、技能和伙伴。2026-11-17 内部 Development 包的九组自动检查全部通过，进程退出码为 0。

目前最大的缺口是验证方式，而不是功能数量：

- 18 单的通过证据是测试程序直接设好完成状态，只证明结算逻辑；还没有一单被“从接单到结算”自然玩通。
- 没人用键鼠玩过新增内容。手感、跑腿时长、动物是否好找都还是未知数。
- 设置功能不全（无键位重绑、多分辨率、界面缩放），中英文本也不完整。
- 项目没有版本控制，靠复制文件夹备份。11-15 的测试存档污染事故说明，现在出错后很难快速回到确定的状态。

所以规划的重心是：先建立能回退的版本管理，再用“像玩家一样操作”的方式把 18 单逐单跑通，最后交给你试玩。

## 3. 玩法建议

### 3.1 狩猎是打磨重点，但玩家要到很后面才接触到

按现有解锁，射击狩猎的主场是 L06（Q16–Q18，建议 Lv18–25）。L01–L05 的星挑战里还有多条“不用直接射击”“不用枪械”。这样玩家前 15 单主要在布笼和清洁，打磨最多的狩猎手感要到最后才出现。

建议（见 5 节 P01）：L02–L05 每张图至少有一单把“潜行接近 + 精确射击”作为好用的路线之一，例如 Q05 屋梁鼠用气枪点射，Q09 狐狸用弓。原有“不用射击”星保留，玩家仍可选择布陷阱。

### 3.2 狩猎手感的三段

潜行射击类游戏的乐趣通常来自三段连贯的反馈。下表对照现有实现，列出缺什么：

| 阶段 | 玩家在做什么 | 现有 | 建议补充 |
| --- | --- | --- | --- |
| 发现 | 找痕迹、听声音、用 Q 和镜具确认 | Q 透墙脉冲、声音方向提示、望远镜、夜视/热像 | 足迹和翻土痕迹能看出方向和新旧；被惊动的动物留下可追的痕迹 |
| 接近 | 控制噪声和视线，找射击位置 | 蹲行无声、噪声值、动物视线 | 在左下 HUD 显示自身“被发现程度”；可选风向，影响犬形和野猪的嗅觉（P03） |
| 出手 | 屏息瞄准、命中、处理结果 | 屏息、气枪/弓/步枪、命中判定 | 命中反馈（击中音、准星确认）；未致命时动物受伤逃跑并留下可追踪痕迹（P02）；弓有可读的下坠 |

“受伤逃跑 + 追踪”是狩猎类游戏最核心的循环之一。基调是轻松的职业模拟，所以痕迹用简单标记表现，不做血腥效果。

### 3.3 星挑战偏向“禁止某物”

54 颗星里有不少是“不用 X”“不用 Y”，属于限制型。限制型星容易做，但玩起来更像打勾。建议每单至少一颗星奖励正向技巧（P04），例如“一发命中击倒指定目标”“30 米外完成射击”“未被目标发现完成猎杀”。这类星正好服务 K04 的狩猎重点。

### 3.4 写实规则的度量

K05 要求先保留写实规则，试玩后再调。为了让“麻烦”有数据，建议每局自动记录以下时间（P07）：

- 跑腿：往返卡车、公司柜台的步行时间。
- 补给：换包、右键补充、修复耐久的时间。
- 搬运：手持笼子、尸体、大货移动的时间。
- 决策动作：观察、布置、瞄准、射击、调查。

初步阈值：一局里前三类合计超过 25%，或单次往返卡车超过 40 秒，就把这一单列入“琐碎报告”交给你决定。阈值本身也可以调。

### 3.5 一局时长与作品集展示

策划目标是首次完整委托 15–25 分钟。18 单按 20 分钟计算，主线约 6 小时，加上重玩会更长。作为作品集，看的人通常只会玩 10–20 分钟。建议在 M5 额外准备一个展示入口（P08）：一份预设存档直接开在一单狩猎委托，加一份一页的玩法说明。这只是一个存档文件，不新建玩法入口。

### 3.6 合同卡信息量

现有合同规则很细（借用、驱离、货物去向、禁用装备）。建议合同卡默认只显示三行：主目标、禁止项、三颗星；其余放在“详情”里展开。这只是界面排版，不改规则。

## 4. 开发建议

### 4.1 Git 与构建管理（K06、K07）

- **仓库根目录**：`G:/MyGame`，`.gitignore` 用白名单，只纳入 `RatControlSimulator/Assets`、`Packages`、`ProjectSettings`、`开发文档/`、策划文档、`AGENTS.md` 和 `图片和附件/`。`Library`、`Temp`、`Logs`、`UserSettings`、`Builds/`、`Backups/`、测试工程和 `_tmp*` 都不纳入。
- **LFS**：`*.fbx *.png *.jpg *.psd *.ogg *.wav *.mp3` 走 Git LFS。GitHub 免费 LFS 额度约 1GB，白模阶段够用，以后加正式美术再评估。
- **构建包不进 Git**：一个 Development 包约 2.6GB，所以只留在本地 `Builds/`。验收版本打 tag（如 `accepted/p0-v4`、`accepted/whitebox-1`），tag 说明里写构建路径和 SHA256。
- **首次提交**：提交当前工程原样，打 tag `baseline/2026-11-18`，不改任何代码。V4 验收时的源码已在 `Backups/BeforeFullWhitebox-20261114-202538`，可以再补一个 `accepted/p0-v4` 提交作为历史起点。
- **推送**：需要你在本会话里输入 `! gh auth login` 登录。直连 GitHub 不稳，推送失败时重试或用你提供的代理，不改用别的托管平台。
- **删除旧构建**：每次验收打 tag 后，列出 `Builds/` 中待删目录（目前是 RiverbendDemo、V2、V2 zip、V3、V3_1、作废的 RiverbendFullWhitebox），你确认后才删。始终保留最新的已验收构建。
- **存档保护**：真实存档 `profile.json` 不进仓库；测试继续走隔离 profile。每批测试前后核对存档 SHA256。

### 4.2 代码组织

你这次没有选择整理旧代码，所以 `DemoGame` 等已验收文件不重构。新增系统继续写进独立的 partial 文件或新类文件，单个新文件尽量不超过约 600 行。这是现有做法，不需要改动旧代码。

### 4.3 验证方式

现有自动检查继续保留，但它们只证明状态和结算逻辑。完整白模还需要两种新的验证：

- **自然通关脚本（P06）**：用 Input System 模拟真实键鼠，让角色沿导航路线走、按 E/Q、放笼、瞄准开火、装车、离场。检查只读合同状态，不直接写“完成”。每单至少跑一次“主任务成功 + 同局三星”。这一步可以在你试玩前发现大部分卡关、无法到达和软锁问题。
- **你的试玩**：手感、可读性和麻烦程度只有人能判断。我无法真正用键鼠玩游戏，之前的 Windows 窗口截图也一直超时，所以 M2 的人工验收要靠你。

### 4.4 试玩辅助（只在 Development 包）

- **测试面板（P05）**：F12 打开，可跳到夜晚、加钱/经验、解锁地图、传送到作业点。Release 包里不编译这部分代码。这样你可以直接测某一单，不用从 L01 一路玩上去。
- **试玩日志（P07）**：每局写一份 CSV 到存档目录，内容是 3.4 节的分类时间、开火/命中次数、被发现次数、各星结果。你只要正常玩，结束后把文件发回来，我据此出调整报告。

## 7. 每批工作的固定步骤

1. 读 `AGENTS.md` 和 UnitySkills 规范，检查 `/health`，确认实例是 `RiverbendRatControlDemo_0D5D9EF7` 对应的 Riverbend Rat Control Demo 工程。
2. 改动前确认工作区干净，没有未提交的修改。
3. 只在原 P0 路径上做局部增量；涉及已验收行为的改动，先向你说明原因和影响。
4. 编译并等待域重载完成，确认错误为 0；串行运行全部检查（含原 `DemoV4Checks`）；核对真实存档 SHA256。
5. 提交 Git，提交信息写清改了什么、跑了哪些检查。
6. 在 `P0沿用与重新实施记录.md` 追加检查点，区分“自动检查通过”“脚本自然通关”“用户试玩确认”三种证据。
